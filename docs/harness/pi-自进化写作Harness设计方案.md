# pi × article-system 自进化写作 Harness 设计方案

> 版本：v1.2（2026-09-20 定稿）· 状态：**定稿**——R1/R2 两轮独立子代理审阅（各 3 major）全部修订，R3 验证复审通过（16/16 修复到位、0 blocker/0 major）
> 基座：pi（earendil-works/pi，本仓 local-custom）+ D:\lgq\ai-official-account\article-system 现有写稿流程
> 定位：把「公众号主笔」的单篇编排流程升级为一个**可复现、可审计、会从自己的审阅结果里进化**的写作 Harness

## 0. 需求映射（本文档对每一句话负责）

| 需求 | 出处 | 本方案落点 |
| --- | --- | --- |
| 以 pi 为基础 | 用户目标 | §3 L1 运行层：pi SDK 宿主 + pi subagent 扩展模式 |

## 1. 两个基座各有什么（现状盘点）

### 1.1 article-system 已有（保留资产）

- **编排命令** `/write-article`：主会话只做「规划→派发→验收→推进」，每阶段派一个子代理，产物落盘交接；`任务计划.md` 记录阶段表（目标/输入/产物/判据/状态），中断可续跑。
- **两条流水线**：模板 A（常规文，S1 素材调研→S2 标题提纲→S3 成稿→S4 润色→S5 终稿审阅→S6 封面配图→S7 提交）与模板 B（精读，S1~S8，多机核与独立复核）。
- **两道工序定义**：`/polish`（A 审计→B 去 AI 味→C 声音校准→D 自查）与 `/review-final`（A 自述事实/B 覆盖完整性/C 翻译忠实度/D 编号一致性/E 程序化体检/F 独立子代理复核+留档）。
- **机核脚本**：`check_quotes.py`（引用块长度）、YAML 头/违禁词/段长等体检项、精读机核脚本（对照原文快照逐行命中）。
- **知识沉淀点**：调研包 `复审记录.md`（两遍发现与采纳留档）、`materials/` 素材库、`references/` 声音样本与 AI 味清单、`topics.md` 选题池。
- **评审纪律**：验收不采信子代理自报成功；重派上限 2 次；每次任务结束 git commit。

### 1.2 pi 已有（运行基座能力）

- **SDK 宿主**：`createAgentSession(options)`（`packages/coding-agent/src/core/sdk.ts`）——可编程建会话，支持 `tools`/`excludeTools` 白名单、`customTools` 注册、独立 `resourceLoader`，适合做无人值守跑批宿主。
- **扩展系统**：`registerCommand` / `registerTool` + 全套生命周期事件（`agent_start/end`、`turn_start/end`、`session_shutdown` 等，`core/extensions/types.ts`），可在宿主上挂审阅循环编排器。
- **官方 subagent 扩展示例**（`packages/coding-agent/examples/extensions/subagent/`）：每个子代理一个**独立 `pi` 子进程**（上下文完全隔离），代理定义是 `agents/*.md`（角色+工具面），工作流预设是 `prompts/*.md`（如 implement→review→fix 链）；支持并行流式与中止传播。
- **会话持久化**：SessionManager/JSONL 会话与压缩，供断点续跑与事后复盘。

### 1.3 病根（为什么现在还不算自进化）

1. **审阅轮数无保证**：模板 A 的 S5 只跑一轮 `review-final`，「至少两审、改后加审」没有制度约束，靠自觉。
2. **发现不回流**：`复审记录.md` 写完就归档，没有机制把重复出现的发现变成新检查项、新规则。同一类错（如「上个月」实为昨天——review-final 里记的那次）在下一篇仍靠审阅者眼力抓。
3. **规则演进无版本**：AGENTS.md 文风规则靠人手零散改，改了没有版本号、没有生效日期、没有回滚。
4. **无度量**：不知道每篇平均几轮收敛、哪类发现最多、机核拦截率多少——没有数字就无法判断进化是否生效。

## 2. 设计原则（继承既有实践，四条取舍先立）

| # | 取舍 | 决定 | 理由 |
| --- | --- | --- | --- |
| T1 | 对话式 slash 编排 vs SDK 常驻宿主 | **双模并存，共用一套盘面契约**：slash 编排（现状）= 对话模式；pi SDK 宿主 = 跑批模式 | 编排逻辑写在 `.harness/` 契约里而不是写死在宿主里，两种模式读同一份契约跑同一个流程，避免双实现漂移；对话模式保留人工拍板交互（标题选择等），跑批模式服务一天一更的量产 |
| T2 | 子代理复用主会话上下文 vs 独立全新上下文 | **独立 `pi` 子进程，全新上下文**（pi subagent 示例模式） | 独立上下文防锚定：审稿人不能看到写手的自我辩护，只看稿。这正是「子 Agent 审阅」的价值所在 |
| T3 | 加审轮数无上限 vs 设软上限 | **软上限 5 轮（R5），触顶停机升级人工** | 用户要求「有问题即使两次以上，改完+1」，R1+R2+加审至 R5 完全覆盖字面；上限只为防两个审稿人对同一处风格各执一词的死循环，触顶是升级不是放弃 |
| T4 | AI 自动改 harness 自上线 vs 提案-拍板 | **提案-拍板**：AI 产出修订提案，人拍板后生效，带版本与回滚 | 对齐 check-cert-rules 自进化实践与「AI 永不单方终审」纪律；公众号是署名产出，规则改坏一篇的成本高于省一次拍板 |

另有一条铁律贯穿全案：**交接靠盘不靠会话**（现状纪律，升格为契约）——所有轮次输入输出都是文件，任何一轮可独立重放。

## 3. 总体架构：五层

```
┌─────────────────────────────────────────────────────┐
│ L5 进化层  发现→候选→影子验证→拍板→版本上线（§5）      │
├─────────────────────────────────────────────────────┤
│ L4 记忆层  .harness/：规格·教训池·指标账本·版本档案（§5.1）│
├─────────────────────────────────────────────────────┤
│ L3 评测层  机核脚本门禁（确定性）+ ReviewSpec 审阅清单（§4.4）│
├─────────────────────────────────────────────────────┤
│ L2 流程层  S1~S8 流水线 + R 审阅循环（R≥2，修复必+1）（§4） │
├─────────────────────────────────────────────────────┤
│ L1 运行层  pi SDK 宿主 / slash 编排 + 独立子代理进程（§3）  │
└─────────────────────────────────────────────────────┘
```

### 3.1 L1 运行层

- **代理编队**（pi subagent 模式，`.pi/agents/` 下四份定义，各配最小工具面）：

| 代理 | 定义文件 | 职责 | 工具面 |
| --- | --- | --- | --- |
| writer | `writer.md` | S3 成稿 / 修复稿 | read/write/edit/bash（跑机核脚本） |
| polisher | `polisher.md` | S4 三道润色工序 | read/edit/bash |
| reviewer | `reviewer.md` | R 轮审阅（每轮一个新进程） | read/grep/ls **纯只读**（不下发 write/edit/bash——审稿人只出报告文本，不改稿不跑脚本；E 类机核由编排方跑完把结果文件喂给它） |
| fixer | `fixer.md` | 按采纳清单修稿 | read/edit/bash（含修复后重跑机核） |

- **代理定义加载**：四份定义放 `.pi/agents/`（项目级）。pi subagent 扩展默认只加载用户级（`agentScope:"user"`），须显式配 `"project"` 或 `"both"` 才加载项目级（本仓为信任仓）；跑批模式无 UI，项目级确认自动跳过。
- **宿主两种形态**：
  - **对话模式**（现有）：ZCode/pi 交互会话里跑 `/write-article`，主会话做编排与验收，子代理经 Agent 工具派发——与 pi 子进程子代理是**上下文隔离等价**而非同一实现，工具面控制粒度不同，故四份代理定义两模式各维护一份、内容同构；
  - **跑批模式**（新增）：`harness/run.ts` 用 `createAgentSession({ tools, customTools })` 起宿主，注册 `run_article` / `evolve` 两个 customTools，从 topics.md 取题无人值守跑完整流水线；产物与状态照写同一套盘面。
- **模型面**：宿主可配模型分级（如写手用强模型、机核执行用快模型），pi 的 `scopedModels`/model 配置原生支持，不在本方案展开。

### 3.2 L2 流程层（流水线总表）

模板 A 升级版（模板 B 映射见下表）：

| 阶段 | 执行者 | 变化点 |
| --- | --- | --- |
| S1 素材调研 | 子代理 | 不变 |
| S2 标题与提纲 | 主会话+用户 | 不变（人工拍板是 L2 唯一交互点） |
| S3 成稿 | writer | 写前必读 `.harness/spec/writer-prompt.md`（含历届教训摘要，见 §5.2） |
| S4 润色 | polisher | 不变（/polish 三道工序） |
| **R1 审阅** | reviewer | **新增独立轮**：修辞性审阅（结构/钩子/金句/段长/AI 味残留），按 ReviewSpec R1 类检查；与 R2 可并行派发 |
| **R2 审阅** | reviewer（新进程） | **原 S5 升格**：事实与完整性审阅（review-final A/D/E/F 类），与 R1 不同视角；与 R1 可并行派发 |
| S5 修复循环 | fixer + reviewer | **新增**：见 §4.3——有问题必加审，修复后 +1 复审干净即终态 |
| S6 封面与配图 | 子代理 | 不变，可与 R 循环并行（无文件竞争） |
| S7 提交汇报 | 主会话 | 增项：写 `.harness/metrics.md` 指标行（§8）+ 发现归档（§5.1） |

模板 B（精读）原 S1~S8 → 新流程映射：

| 原阶段 | 去向 | 说明 |
| --- | --- | --- |
| S1 抓取备料 | 不变 | — |
| S2 通读稿 / S3 引申与读后感 | writer | 写前同样读 writer-prompt 最新版 |
| S4 机核 | 前置门禁 | 机核不占 R 轮数（与模板 A 同口径）；对照快照逐行命中是进入 R 轮的入场券 |
| S5 独立复核 | R1 + R2 | 直译忠实度（原 review-final C 类）归 R2；**R1 的 AI 味/声音类检查只施于自述部分**，直译与原文框以忠实为先、不做修辞审阅；「直译两遍复审」保留，作为 R2 C 类执行两遍 |
| S6 修稿与终稿审阅 | S5 修复循环 | 采纳清单修稿 + §4.3 加审规则，与模板 A 完全一致 |
| S7 封面 | 不变 | 可与 R 循环并行 |
| S8 提交汇报 | S7 同款 | 含 metrics 记账与发现入池 |

**机核（check_quotes.py、违禁词、YAML 头、精读逐行命中）是 R 轮的前置门禁而不是审阅轮次**：E 类机核脚本每次修复后必须重跑，全绿才允许进入下一轮人工类审阅。机核不占 R 轮数——它是流水线的一部分，就像编译一样。

### 3.3 关键纪律（从现状升格为硬约束）

- 审阅者**纯只读**（T2 的落地：工具面不下发 write/edit/bash，由 pi 工具注册层强制，不靠提示词自觉）；
- 修复者（fixer）只按采纳清单改，不做清单外「顺手优化」——防止修稿引入新问题导致轮数爆炸；
- 每轮审阅产物是独立文件 `复审-R{n}.md`，**由编排方（主会话/宿主）把审稿人返回的报告文本落盘**——审稿人自己无写权限，两模式的落盘路径与格式用同一套契约；主会话汇总进 `复审记录.md`，且不复用上一轮审稿人的上下文。

## 4. 审阅循环（本方案核心）

### 4.1 固定两轮：R1 + R2

每篇成稿（S4 润色完成后）**默认至少两轮审阅**，两轮不同视角、各自独立子代理：

| 轮次 | 视角 | 检查范围 | 对应现有资产 |
| --- | --- | --- | --- |
| R1 修辞审阅 | 「编辑」：这稿读起来如何 | 结构与钩子、金句质量与数量（2~3）、段长、AI 味残留（16 模式清单）、小标题风格、互动引导与话题标签合规 | /polish 阶段 A 的审计清单 + AGENTS.md 文风规则 |
| R2 事实完整性审阅 | 「主编」：这稿可信吗 | 自述事实与相对时间词、跨文章引用、归因句、编号与内部一致性、覆盖完整性（精读）、翻译忠实度（精读）、程序化体检复核 | /review-final A~F 类 |

两轮都通过（无 blocker/major）才算成稿（完整终态定义见 §4.3）。**两轮视角刻意错开**：R1 挑「不好读」，R2 挑「不可信」，避免两轮重复劳动，也让「至少两审」不只是同一件事做两遍。

### 4.2 审阅产出契约（结构化，进化层的燃料）

每轮 `复审-R{n}.md` 必须包含机器可读的发现清单：

```markdown
## 发现清单
| ID | 类别 | 严重度 | 位置 | 描述 | 模式标签 | 建议动作 |
| R2-01 | 自述事实 | blocker | L42 | 「上个月」实为 2026-09-19 | 相对时间词 | 改为绝对日期 |
| R1-03 | AI味 | minor | L17 | 「值得注意的是」 | 模式#7 | 删 |
## 结论
通过 / 不通过（blocker/major 计数：X）
```

- **严重度三档**：`blocker`（事实错误、违禁词、来源缺失——不改不能发）、`major`（逻辑断裂、覆盖缺口、引用超限未分框）、`minor`（风格瑕疵，不阻塞发布）。
- **模式标签**受控词表（相对时间词 / 绝对化用语 / AI味#N / 引用块超限 / …），词表本身在 `.harness/spec/` 里版本化——这是 §5 毕业管道的聚类键。
- 发现清单之外，审稿人可附**正面发现**栏（可选，无严重度）：判定优秀的金句、结构、开头钩子——这是 §5.2 出口④ 的唯一入口，防止进化只收敛「不犯错」而不累积「做得好」。

### 4.3 加审规则（有问题就多审，改完必 +1）

```
R1、R2（可并行）→ 汇总全部发现 → 有 blocker/major（含 minor 折算）？
  ├─ 无 → 成稿 ✅（首轮即全净）
  └─ 有 → 修稿 F1 → 加审 R3 → 仍有？
            ├─ 无 → 成稿 ✅（修复后 +1 复审干净即终态）
            └─ 有 → 修稿 F2 → 加审 R4 → …（软上限 R5，触顶升级人工）
```

**终态定义（全文唯一口径）**：**修复后 +1 复审干净即收敛**——加审轮无 blocker/major（含折算）即成稿，不要求再追加一轮；R1、R2 首轮即全净同样直接成稿。这正对齐用户口径「改完以后还要 +1 次审阅」：+1 那轮干净就是终点。

规则逐条：

1. **R1、R2 都审完才进入修复**（先收集全部问题再修，避免修一处审一处把轮数撕碎；两轮无文件竞争、可并行派发，汇总后统一判定）。
2. 任一轮出现 **blocker 或 major**（含 minor 折算）→ fixer 按采纳清单修稿 → **必加一轮复审 R(n+1)**。
3. **加审轮的审阅范围由宿主按规则拼装**（不靠审稿人自定）：**上轮全部未通过视角做全量检查 + 已通过视角只对修改段落做回归抽查**（验证修复没改坏别处），并重跑 E 类机核——机核全绿是复审报告的入场券。
4. **终态即第 3 步的加审轮干净**（见上方终态定义）；再有新 blocker/major → 再修再 +1，循环，至多到 R5（下条）。
5. **软上限 R5**：第 5 轮复审后仍有 blocker/major，停机，主会话把各轮记录与分歧点呈给用户拍板（T3）。超过 3 轮通常不是稿子问题而是规格问题（两轮审阅人对同一标准理解相反），此时该触发的是 §5 的规则修订提案而不是继续改稿。
6. **minor 不触发加审**，挂账进发现清单；**折算口径**：按「模式标签 + 所在段落」去重后的全篇累计（跨轮合并，同处重复报告只计一次），累计 ≥5 个（`harness.config.json` 可调）折算 1 个 major 进入修复；修复后剩余 minor 重新计数，低于阈值不再阻塞。
7. **复审轮独立进程**：验证修复的 R(n+1) 同样是新子代理，读「上轮发现清单 + 采纳清单 + 当前稿」，不知道也不读 fixer 的辩护——只对盘不对人。

### 4.4 ReviewSpec：审阅清单声明化

把散在 `/review-final` 与 `/polish` 里的检查项抽成 `.harness/spec/review-spec.md`（版本化），每条检查项四元组：

```
[类别] [严重度默认值] [检查描述] [模式标签]
```

- R1/R2/加审轮的 prompt 由宿主按 §4.3 规则 3 的范围从 ReviewSpec 拼装——**审什么由规格决定，不由当轮审稿人心情决定**，这是轮次间可比、指标可算的前提；
- `/review-final` 与 `/polish` 阶段 A 的检查项**都迁移进 ReviewSpec**（单一权威源）：两个命令文件保留入口与工序步骤，检查项定义一律改为引用 ReviewSpec，不允许两处各留一份；
- §5 毕业管道产出的新检查项，落点就是 ReviewSpec 的新条目（带版本号），机核可判定的落点是新 `check_*.py` 断言。

## 5. 进化层：从「审出问题」到「下次不犯」

核心闭环（对齐 generate→evaluate→diagnose→persist）：

```
发现(结构化) → 聚类(模式标签) → 候选池 → 影子验证 → 用户拍板 → 版本上线 → 效果回看(metrics)
      ↑                                                              │
      └──────────────── 下一篇 S3/S4/R 轮使用新规格 ←──────────────────┘
```

### 5.1 L4 记忆层：`.harness/` 盘面契约

```
article-system/
  .harness/
    harness.config.json      # 阈值：minor→major 折算数(默认5)、软上限(默认R5)、
                             #   毕业阈值(默认同标签≥2次)、影子回看篇数(默认3)
    spec/
      review-spec.md         # ReviewSpec 审阅清单（版本化，§4.4）
      writer-prompt.md       # 写手提示词补充（版本化，含教训摘要）
      pattern-tags.md        # 模式标签受控词表
    lessons/
      pending.md             # 候选池：未被毕业的发现聚类（自动追加）
      adopted.md             # 已采纳：每条带来源复审ID、生效版本、回滚点
    metrics.md               # 指标账本：每篇一行（§8）
    pending-decisions.md     # 跑批模式挂起的拍板项（S2 标题、毕业拍板），人回来续跑
    archive/                 # 归档：历史提案、拍板记录、退役版本
  （现有：output/ 下的 任务计划.md、复审记录.md、复审-R1.md…R{n}.md 照旧落调研包）
```

原则：**记忆层只增不改写历史**——复审记录与指标是账本，append-only；规格修订走版本号，旧版进 archive 可回滚。

### 5.2 四个沉淀出口（按成本从低到高，对齐五级阶梯）

| 出口 | 触发条件（默认，config 可调） | 产物 | 落点 |
| --- | --- | --- | --- |
| ① 机核脚本晋升 | 同模式标签发现 ≥2 次，且判定可确定性化（正则/计数/对照命中） | 新检查断言提案 | `scripts/check_*.py` 新增断言 + ReviewSpec 对应条目标注「已机核化」 |
| ② ReviewSpec 修订 | 同类发现 ≥2 次但需语义判断（如新发现的归因句变体） | 新检查项/严重度调整提案 | `spec/review-spec.md` 新条目（版本 +1） |
| ③ 写手提示词修订 | 发现的根因在写法而非审法（如「开头钩子总写得太弯」） | 提示词增补提案 | `spec/writer-prompt.md`（版本 +1） |
| ④ 样本库扩充 | 任意一轮 R{n} 报告「正面发现」栏（§4.2）里的优秀金句/结构 | 候选样本提案 | `references/` 声音样本或 `materials/benchmarks/` |

规则：**S3 写手每次开工读 `lessons/adopted.md` 的当前生效摘要 + writer-prompt 最新版**——进化结果在下一篇文章的源头就生效，而不是只让审稿人更严。

### 5.3 毕业管道（候选 → 上线）

1. **归档即入池**：S7 提交时，主会话把本篇全部发现按模式标签 append 进 `lessons/pending.md`（机械操作，可由宿主 customTool 自动做）。
2. **触发评估**：pending 里同标签计数达到毕业阈值（默认 ≥2），宿主生成修订提案（用 LLM 起草，人拍板）。
3. **影子验证**：提案的新检查项先只跑「回看」——对最近 3 篇已发布文章离线跑一遍，报告假如有它会报什么，**命中清单随提案一并呈用户，用户拍板时逐条标注命中真值（真问题/误报）；误报率 >50%（可调）当场打回重写**，不进正赛。
4. **拍板上线**：用户拍板 → 规格文件版本 +1，旧版本移入 archive，`adopted.md` 记录来源与生效版本。
5. **回看退役**：上线后下一个毕业周期检查该条目的命中质量，连续 2 个周期零命中或纯误报 → 提案退役（移回 archive），防规格膨胀。

**AI 不自动改规格、不自动改脚本**（T4）：宿主能自动做的是「聚类计数、起草提案、跑影子验证、记账」，改 spec/脚本的 diff 一律等拍板。

### 5.4 精读与常规文共用机制

模板 B 的机核（对照原文快照逐行命中）已是确定性检查，直接是 ① 号出口的既有范例——本方案等于把它推广成所有可确定性化检查的通用路径。

## 7. 失败与边界

- **审稿人分歧**（R1 说好 R2 说坏同一处）：以更严的为准；若确属标准模糊，触发 ② 号出口补检查项定义。
- **修复引入新问题**：回归抽查 + 机核重跑兜底；同一段落连续两轮返工，fixer 停手，升主会话判断是写手能力问题还是提纲问题。
- **跑批模式无人拍板**（S2 标题选择、§5.3 毕业拍板）：跑批模式把拍板项写 `pending-decisions.md`，流程挂起在该阶段，人回来续跑——与「任务计划.md 断点续跑」同一机制。
- **成本失控**：每篇 R 轮成本可从 metrics 直接读出；软上限 R5 + 「先收集后修」两条已把最坏轮数封死（R1+R2+R3+R4+R5 = 5 次审阅上限）。
- **机核误报**：与审阅发现同一管道退役（§5.3 第 5 步「回看退役」），不搞只进不出。
- **过程审计边界**：pi 子进程子代理以 `--no-session` 运行，R 轮子进程自身不留 JSONL 会话；过程审计完全依赖盘面文件（复审报告、采纳清单、metrics）——与「交接靠盘」铁律一致，但须知会话回放对子代理轮次不适用。

## 8. 度量（进化是否生效看这里）

`metrics.md` 每篇一行：

```
日期 | 标题 | 类型 | R轮数 | blocker数 | major数 | minor数 | 高频模式标签 | 机核拦截次数 | 规格版本 | 备注
```

- 标题等自由文本字段写入前清洗：`|` 替换为 `/`、换行替换为空格，防破行。

月度回看三个数：

1. **轮数分布**：目标多数文章 2 轮收敛；R≥4 占比持续 >20% 说明规格或写手提示词有系统性问题（触发专项修订而非继续挨篇修）。
2. **迁移信号**：某模式标签的发现数在毕业上线后应逐月下降——下降即进化生效的实证；不降说明出口选错层（该走 ①机核化 的走了 ③提示词）。
3. **人工兜底率**：推送到发布后被人工抓出的问题数（从飞书反馈/自察收集）——这是最终真值，Harness 的目标是把它压到接近零。

## 9. 本设计方案的定稿流程（吃自己的狗粮）

本文档自身按 §4 的循环审阅：

1. **R1**（流程视角子代理）：审阅循环逻辑、轮次规则、与现有流程的兼容性、规则完备性；
2. **R2**（技术视角子代理）：pi 接口引用准确性（sdk.ts / extensions / subagent 示例的实际能力）、落盘契约可实施性、成本与边界情形；
3. 两轮发现合并采纳修订后，**+1 轮复审验证**（确认修复到位且未改坏）——即用户要求的「改完以后还要 +1 次审阅」；
4. 终态（§4.3 唯一口径）：复审轮无 blocker/major → 定稿。三轮审阅报告落盘本文档同目录：`*-复审-R1.md`、`*-复审-R2.md`、`*-复审-R3.md`。
