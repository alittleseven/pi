## 一、article-system 已有资产的优化对照

主方案对 article-system 的总原则是**资产不推翻，制度补三层**：检查项规格化、审阅轮次制度化、发现回流制度化。逐项对照：

| 已有资产 | 现状 | 主方案的优化 | 明确不动的部分 |
| --- | --- | --- | --- |
| `/write-article` 编排 | S5 单轮终稿审阅，轮数靠自觉 | S5 拆 R1（编辑视角）+ R2（主编视角）双轮 + 修复循环（问题必 +1 复审，软上限 R5）；计划表加 R 轮次列；判据改"终态达成" | "规划→派发→验收→推进"骨架、五要素 prompt、验收不采信自报 |
| `/review-final` | A~F 检查项写死在命令文件里，一次性使用 | 检查项迁移 ReviewSpec（版本化 + 受控模式标签），命令文件保留为 R2 入口只做引用——检查项因此可聚类、可毕业、可回滚 | A~F 的检查内容本身、精读机核脚本 |
| `/polish` | 四阶段流程（其中 B/C 为两道改写工序）+ 阶段 A 审计清单 | 阶段 A 清单并入 ReviewSpec R1 类（单一权威源）；工序保留 | A/B/C/D 工序划分、样本优先于清单原则 |
| 机核脚本（check_quotes.py 等） | 散点体检，跑不跑看自觉 | 升格为 L3 门禁：R 轮入场券 + 修复后必重跑；成为毕业管道出口①的落点（新检查以新增断言上线，须拍板） | 既有脚本行为不变 |
| 复审记录.md | 事后留档，写完即沉 | 发现结构化（严重度 + 模式标签 + 正面发现栏），成为进化燃料：按标签聚类入 pending 池 | 留档位置（调研包）与逐轮记录格式 |
| AGENTS.md 文风规则 | 唯一行为基准，人手改、无版本 | 正文不动；上面叠 `.harness/spec/` 细化层，冲突以 AGENTS.md 为纲 | 全部正文规则 |
| references/ 与 materials/ | 静态样本与素材 | 成为出口④落点：审阅正面发现回流扩充样本 | 内容与结构 |
| 任务计划.md 续跑 | 会话中断续跑 | 升格为统一断点机制：跑批模式拍板挂起（pending-decisions.md）同款 | 机制本身 |
| `/push-draft`、`/collect-materials`、`/company-intel` 等其余命令 | — | push-draft 仅前置条件改为 R 终态；其余不在主方案处置范围，维持不动 | 全部 |
| （无） | 度量缺失 | 新增 metrics.md 指标账本与月度回看三数 | — |

一句话：原来靠"主笔自觉"的三件事——复审做几轮、发现往哪放、下篇怎么变好——全部变成流水线步骤。

## 二、pi 在方案中的不可替代性

诚实结论先行：**M1 对话模式下 pi 没有不可替代性**——slash 编排 + 子代理派发在 ZCode/Claude Code 里都能跑，主方案的对话模式本来就被设计为"上下文隔离等价"（而非同一实现）。pi 的不可替代性在 M2 之后的四层，一层比一层难在别处复刻：

1. **工具注册层强制（硬安全边界）**：reviewer 纯只读不是提示词说"请你别写"，而是 tools 白名单下根本不注册 write/edit/bash——pi subagent 的代理工具面经 `--tools` 下发，机制有源码支撑。注意官方示例的 reviewer.md 白名单含 bash（其自述"工具权限并非完全可强制"），落地须像主方案 §3.1 那样显式收窄为 read/grep/ls。收窄后审稿人物理上无法改稿、无法跑脚本——这是"审改分离"的实现基础，多数宿主只能做到提示词约束。
2. **跑批宿主形态**：`createAgentSession` 提供了"宿主程序里嵌会话"的公开 SDK——工具白名单、customTools、scopedModels（写手强模型 / 机核快模型分级）都是构造参数。一天一更的量产能无人值守跑，靠这个形态，不靠人肉开 N 个会话。
3. **模型无锁定**：pi 经 pi-ai compat 层 provider-agnostic，换模型是配置不是代码。成本敏感场景（每篇 5~10 个子代理调用）下，把审稿人切便宜线、或整线迁国产模型，是配置操作。本机火山/智谱双订阅线并持的现实下，这是实质能力。
4. **harness 自身可改（自进化的深层含义）**：进化阶梯"改提示词→改规格→改代码/harness"，第三级只有开源、本仓 local-custom 可改的 harness 能走。pi 扩展是 TypeScript、examples 齐全、官方 subagent 示例可直接抄——主方案的宿主、门禁钩子（发现入池、metrics 记账做成事件钩子而非靠主会话记得做）都建立在这上面。闭源宿主到这一级就断了。

对照既有结论：《pi 完全替代 ZCode 方案报告》（同目录 pi-完全替代ZCode方案报告.md）的口径是 pi 替代日常交互"85% 可替代、2 项硬差距（桌面端 GUI、浏览器深度控制）"——那是把 pi 当**日用交互端**衡量的维度。本方案把 pi 当**可编程运行基座**，不碰 GUI/浏览器，依赖的恰是其可控性与模型自由度；两份结论维度不同，并不冲突。

## 三、article-system 仓与 pi 仓的关系

一句话：**article-system 是报社，pi 是印刷机厂**。报社的流程规章（.harness/ 契约、命令、素材、成稿）不进印刷机厂；印刷机厂不 care 印什么。

- **依赖方向单向**：article-system → pi（运行时用 pi 的引擎能力），pi 对 article-system 零感知。`harness/` 宿主代码建在 article-system 仓内（M2），import pi 的包或 spawn pi CLI；pi 仓只在需要改引擎级行为时才动（local-custom 加法式修改，跟上游 rebase 的 fork 纪律照旧）。
- **数据不出业务仓**：.harness/ 记忆、output/ 产物、metrics 全在 article-system 仓，git 版本化，随仓 clone 走（A 机 ↔ B 机同构）。pi 仓里没有任何一篇文章的记忆。
- **版本策略**：harness 对 pi 的依赖钉精确版本；pi 上游更新先在 pi 仓 rebase local-custom 验证，article-system 仓择机升依赖。
- **与圈 2 拍板的衔接**：圈 2 已拍板 D1=形态（SDK 嵌入宿主）、D4=落点（a-pi-space 独立仓，npm 锁版本），两者互补而非互斥。本写作 harness 是领域实例：形态同 D1（spawn CLI / SDK import，不动 pi 仓主线）；落点暂驻 article-system 业务仓而非 a-pi-space——因它强依赖业务仓的 scripts/*.py 与 output/ 结构。若日后把"审阅循环"抽象成通用能力，再考虑并入 a-pi-space 独立仓（届时即 D4 形态）。

## 四、主方案的记忆设计盘点

主方案的记忆按载体分**六类**，各有写入/读回时机。其中参数/规格/经验/账本/决策五类落在 .harness/（主方案的 L4 记忆层），过程记忆在 output/ 调研包——按主方案属流程盘面而非 L4，本文并入盘点只为完整：

| 类别 | 载体 | 写入时机 | 读回时机 |
| --- | --- | --- | --- |
| 参数记忆 | harness.config.json | 拍板时改 | 宿主/编排方启动时 |
| 规格记忆 | spec/review-spec.md、writer-prompt.md、pattern-tags.md | 毕业拍板后版本 +1 | 每轮 R 拼装 prompt；writer 开工 |
| 经验记忆 | lessons/pending.md → adopted.md | S7 发现入池（append）；毕业时迁移 | writer 开工读 adopted 生效摘要 |
| 账本记忆 | metrics.md | S7 每篇一行（append-only） | 月度回看聚类 |
| 过程记忆 | output/ 调研包（任务计划、复审-R{n}、复审记录） | 各阶段落盘 | 断点续跑；毕业管道回看 |
| 决策记忆 | pending-decisions.md、archive/ | 挂起/退役时写入 | 人回来续跑；回滚时 |

四个设计特征（这是它与"给 agent 挂个记忆库"的常见做法的区别）：

1. **记忆即盘面**："交接靠盘不靠会话"的延伸——记忆也靠盘。人类可读、git 可审计、clone 即带走，不依赖任何外部服务活着。
2. **分级而非一个大池子**：参数/规格/经验/账本/决策各有载体、各有 append 或 version 规则。规格可版本回滚，账本只增不改，经验有毕业与退役。
3. **写入时机制度化**：入池是 S7 流水线步骤、毕业是周期评估、修订必拍板——agent 没有"自由写记忆"的权限，防止记忆污染。
4. **读回时机制度化**：记忆的价值在"下次开工被读到"——writer 开工必读 adopted 摘要、reviewer 必按 ReviewSpec 拼装、月度必看 metrics。没有读回路径的记忆条目不配存在（退役机制兜底）。

**主方案未涉及的**：语义检索记忆（素材检索已有 materials.py + git，够用）、对话记忆（每篇即弃，靠盘面）。这是第五项的引子——那 OV 在哪里排上用场？

## 五、记忆独立与 OV 协同

结论先行：**主方案的记忆本来就不走 OV**——.harness/ 是仓内文件，这是对的：写作流水线每一步读什么写什么都是确定性路径，不该依赖一个常驻服务。要设计的是第二层：OV 作为**慢记忆桥**选择性接入，拿它真正独有的两样东西——**跨项目语义召回**与**个人级偏好沉淀**。

### 5.1 分工判据（一句话版）

**确定性读回走盘面，语义搜索与跨仓经验走 OV。**

- .harness/（项目级、结构化、确定性读回）："这篇流程下一步读哪个文件"。
- OV（个人级、跨项目、语义检索）："我以前遇到类似问题怎么定的"、"用户对公众号写作有哪些已固化的纠偏"。

### 5.2 两层架构

```
┌─ 慢记忆层（OV，可选增强，失败静默降级）──────────────────┐
│  下行召回：仅两个工具级调用点 = S1 调研子代理、月度回看例程  │
│  上行沉淀：月度回看摘要 + harness 里程碑 → OV 记忆（拍板后）│
├─ 主记忆层（.harness/，仓内，零外部依赖）─────────────────┤
│  参数 / 规格 / 经验 / 账本 / 决策 盘面（主方案原样）        │
│  关键路径（S1~R 循环~S7）只读写本层；S3 写手不接 OV        │
└────────────────────────────────────────────────────┘
```

三条实施要点：

1. **OV 不进关键路径**：跑批宿主 run.ts 不 import OV、不等待 OV。OV 的工具级调用点只有两处——S1 调研子代理带只读 OV 查询工具（search/read，不给写，与最小工具面哲学一致）、月度回看例程读 OV 历史教训做对照；**S3 写手不接 OV**（偏好经 writer-prompt/adopted 确定性读回，写手保持最小工具面）。查询超时预算 10 秒（config 可调），超时/失败 → 跳过并在调研包留一行「OV 召回跳过（原因）」，流水线照跑。对话模式下本机 ZCode 的 OV hooks 自动注入属"白赚"，不作为依赖；R 轮审稿子代理不消费 OV 注入（对齐 T2 隔离）。
2. **主本唯一，上行为派生**：推到 OV 的内容一律从 .harness/ 派生（月度回看摘要、"相对时间词错误本季 3 起"这类升到个人级的教训）。**上行走拍板**：月度回看例程产出"拟上行清单"随回看报告呈用户，拍板后才写 OV——主方案"agent 无自由写记忆"的原则同样约束 OV。tag 固定为 `harness:article-system`；OV 条目正文须写来源指针（仓内相对路径 + 所依据的主方案版本，如 `出处 .harness/lessons/adopted.md @ 主方案 v1.2`），两机同构路径可直接定位。**OV 不存项目记忆副本**——双主本必然漂移，OV 只存"指针 + 已通用化的跨项目教训"。
3. **升降级判据明确**：升 OV 的候选由月度回看例程按"跨项目仍然成立"提名（如审阅纪律、相对时间词教训），人拍板定夺；只在公众号写作成立的留在 adopted.md。反向：OV 召回与 hooks 注入的内容进正文前按现有素材纪律过来源核查——与素材同权，不因来自记忆库就免检；**注入内容与仓内盘面冲突时以盘面为纲**（AGENTS.md > .harness/spec > OV 注入）。

### 5.3 这样设计拿到什么

- **独立性**：git clone 到任何机器（含 B 机），流水线 + 全部主记忆即刻完整可用，OV 服务停了零影响。
- **OV 的价值不被浪费**：写作偏好类个人记忆（终稿审阅纪律、写作与改稿偏好等 OV 现成记忆卡——已验证在 OV 实存）在 S1 调研召回时提前校准选题与口径；跨项目教训（如 check-cert-rules 沉淀的审阅实践）可被写作 agent 复用。
- **账本不重复建设**：OV 有自己的会话/事件记忆机制，本方案不往里塞 metrics 级细账——那是 .harness/metrics.md 的事，OV 只收派生摘要。
