# pi × article-system 自进化 Harness：替代假设与砍单分析

> 版本：v1.2（2026-09-20 定稿）· 状态：**定稿**——R1/R2 两轮独立子代理审阅（1+2 major）全部修订，R3 验证复审通过（0 blocker / 0 major / 2 minor 已修）
> 前置文档：[主方案](pi-自进化写作Harness设计方案.md) v1.2、[答疑与记忆设计](pi-自进化写作Harness-答疑与记忆设计.md) v1.2（下称"答疑"）
> 问题：pi 会被其他 agent 替代吗（ZCode / Claude Code / WorkBuddy / OpenCode / Codex…）？假设真换了，主方案里有没有需要砍去的？
> 本文性质：假设性方案分析，不改主方案与答疑文档任何结论；替代是假设推演，不是迁移计划。

## 一、先框住问题：替代的到底是什么

主方案里"pi"只出现在 L1 运行层；L2 流程规则（R 循环）、L3 评测（机核 + ReviewSpec）、L4 记忆（.harness/ 盘面）、L5 进化管道全部是 article-system 仓内的平台无关资产。答疑 §二已给出基准结论：**M1 对话模式下 pi 无不可替代性；不可替代性在工具注册层强制、跑批宿主、模型无锁定、harness 自身可改四层**。

所以替代问题 = "这四层在别家能不能找到等价物，找不到的砍不砍"。替代的对象是 L1 引擎，不是这套 Harness。

## 二、候选替代者能力矩阵

事实等级标注：【验·实测】=本会话/本机可复核实证；【验·记忆】=本机记忆级实证、盘面不可复核；【引】=既有报告/文档引述，未本机核实；【无】=未安装未核实。

| 能力维度 | pi（基线） | ZCode | Claude Code | OpenCode | Codex | WorkBuddy/CodeBuddy |
| --- | --- | --- | --- | --- | --- | --- |
| M1 对话编排（slash 派子代理） | 有 | 有（当前宿主）【验·实测】 | 有（本机 headless 可用）【验·记忆】 | 大概率有【引】 | 未核实【无】 | **有——.workbuddy 命令镜像在盘（间接证据）**【验·实测】 |
| 子代理上下文隔离（审稿人不读写手辩护） | 独立 pi 子进程 | Agent 工具隔离，只读型子代理类型存在（Explore 类）【验·实测】；动态工作流子代理无逐代理工具面【引】 | Agent 工具隔离，Explore 只读【引】 | agent 机制【引】 | 无多代理概念【引】 | 未核实【无】 |
| 审稿人只读的注册层强制 | --tools 收窄 read/grep/ls（官方示例含 bash，须显式收窄，见答疑 §二.1） | Agent 工具路径：只读型/声明工具面的子代理类型存在【验·实测】；工作流路径：无逐代理工具面，只读靠提示词【引】 | 自定义 agent 定义可限工具 + headless --allowedTools【引】 | agent 权限配置【引】 | exec 沙箱可只读【引】 | 未核实【无】 |
| 跑批宿主（程序化驱动整条流水线） | 宿主=createAgentSession（圈2 D1 拍板；实现按实现Spec §5 收窄为 adapter 纯 spawn CLI）；子代理=spawn `pi --mode json -p --no-session` | 动态工作流引擎可表达 R 循环控制流（类型化子代理+world.run+日志重放），但受两限：逐 run 用户审批、world.run 命令集提交时冻结——不满足 M2 无人值守【引·SKILL.md】 | headless -p 逐次调用（PowerShell 通道）【验·记忆】 | headless run【引】 | exec 非交互【引】 | 未核实【无】 |
| 模型自由度（写手/审稿人分级、换线） | provider-agnostic | subagent_model 为 run 级（整批子代理同模型），非逐代理分级【引·SKILL.md】；整体绑定所配 plan | 订阅绑定为主【引】 | provider 可插拔【引】 | 绑定 OpenAI【引】 | 未核实【无】 |
| 开源可改（进化阶梯第三级） | 本仓 local-custom 可改 | 闭源【验·记忆】 | 闭源【验·记忆】 | **开源**【引】 | 开源【引】 | 闭源【引】 |

逐家一句话结论：

- **ZCode**：M1 即刻可跑（就是现状）；M2 形态变且打折——动态工作流引擎能表达 R 循环控制流、world.run 能跑机核、日志重放近似断点续跑，但逐 run 审批与命令集冻结使它不满足无人值守，适合对话模式增强或半自动跑批，真跑批仍要走 Agent 工具路径编排。四层不可替代物里它只补齐跑批宿主一层（带上述保留）；只读强制仅 Agent 工具路径成立，模型为 run 级非逐代理；丢"开源可改"。
- **Claude Code**：M1 可跑；M2 走 headless -p 逐次 spawn，PowerShell 通道本机已实证。只读强制靠 --allowedTools 与自定义 agent 工具面。模型自由度与开源可改两层弱。
- **OpenCode**：唯一"开源 + provider 可插拔"双全的候选，四层保留最完整（本机装的是 opencode-ai 1.18.31，agent 权限配置细节未核实）；若替代，它是损失最小的一档。
- **Codex**：据引述绑定 OpenAI 且无多子代理概念【引】——若属实，R1/R2 并行退化为串行两次独立调用；隔离语义仍可保（编排方只把发现清单喂给下一轮、不传上一轮审稿人报告，同主方案 §4.3 规则 7 纪律），故仍满足"至少两审"，模型分级砍。最不划算的一档。
- **WorkBuddy/CodeBuddy**：M1 有间接证据（.workbuddy/commands 镜像在盘，属既有双平台机制；.codebuddy 目录仅 memory/ 无命令面）；M2 能力面完全未核实，本文不给结论、只列为"对话模式兜底"。

## 三、替代假设下的砍单清单（核心交付）

把主方案逐节过一遍，分三档：**不用砍 / 改形态不砍 / 真要砍**。

### 3.1 不用砍的（主方案的主体，全部平台无关）

- T1 双模架构与"交接靠盘"铁律——正因为契约在盘面不在引擎，才谈得上替代；
- `.harness/` 全部盘面契约（config、ReviewSpec、writer-prompt、pattern-tags、lessons、metrics、pending-decisions、archive）；
- §4 审阅循环全部规则（R1/R2 视角、加审必 +1、软上限 R5、minor 折算、终态定义）；
- §5 毕业管道（聚类、影子验证、拍板、回滚）与四个沉淀出口全部——出口①的产物是平台无关的 python 新断言、出口②③④落在 ReviewSpec/writer-prompt/样本库，无一依赖 pi；
- 机核脚本与"E 类门禁"（python 脚本谁都能 spawn）；
- M1 对话模式实现（命令文本本就跨平台，.workbuddy 镜像现成）；
- 答疑 §五 记忆两层架构（OV 桥的调用点在流程侧，与引擎无关）。

### 3.2 改形态不砍的（换引擎 = 重写适配层，设计不动）

| 主方案条目 | pi 形态 | 替代后形态 |
| --- | --- | --- |
| §3.1 四代理定义（.pi/agents/*.md） | pi subagent frontmatter | 各平台代理定义（ZCode agent type / CC 自定义 agent / OpenCode agent 配置），内容同构迁移 |
| §3.1 跑批宿主 | 宿主=createAgentSession（D1 拍板；实现按实现Spec §5 收窄为 spawn CLI）；子代理=spawn `pi --mode json -p --no-session` | **agent-adapter 接口**：`spawnAgent(definition, prompt, allowedTools, model?) → 报告文本或错误` + `runChecks()` 两个原语，背后按平台各写一份实现（ZCode 的工作流引擎可表达控制流但受审批/命令集限制，见 §二，不宜作无人值守实现） |
| 审稿人纯只读 | --tools 收窄 read/grep/ls | 各平台等价机制（见矩阵行三）；实在没有注册层强制的平台，降级为"沙箱只读 + 编排方落盘"组合 |
| 模型分级（写手强/机核快） | scopedModels | 平台支持则配置映射，不支持则降级单模型（worst case 归入 §3.3 第 3 条） |

这一档的本质：M2 的半天 spike 本来就要钉死 spawn 细节，替代假设只是把"钉死 pi 的细节"换成"钉死 adapter 接口 + 各家一份实现"。**适配层是替代假设下唯一值得提前做的设计增量**——给 run.ts 定一个不超过两个原语的接口，pi 只是第一份实现。

### 3.3 真要砍的（三样，全是锦上添花项）

1. **事件钩子层（出处：答疑 §二.4，非主方案机制）**：原设想"发现入池、metrics 记账做成 agent_end/session_shutdown 事件钩子"，定位是不靠主会话记得做的可靠性优化；主方案 §5.1 的机制本就是 S7 显式步骤 + 宿主 customTool。替代后各平台钩子语义不一，砍掉，统一为 M2 状态机显式步骤——零功能损失（钩子本来就不是机制，且 M3"自动入池/记账"验收由状态机满足）。
2. **进化阶梯第三级的"改 agent 运行时"（答疑 §二.4）**：闭源平台上收窄为"改编排器与适配层"——run.ts 是我们自己的代码，永远可改；丢的只是改 pi 核心行为的能力。OpenCode 替代时此档部分保留。
3. **细粒度模型分级（scopedModels）**：平台不支持按子代理指定模型时降为单模型。影响的是成本优化空间，不是流程正确性。

另：主方案 §1.2 的会话持久化（SessionManager/JSONL）在主方案 §7 已定性为可静默放弃项（子代理 --no-session、审计靠盘面），替代后无对应物也不需要——不入三档，随引擎走。

**结论：主方案没有"换底座就必须砍掉"的不可让步项。** 需要砍的三样合计损失：一次显式调用、一层运行时自改权、一部分模型成本优化——都不触碰 R 循环、契约与进化闭环本身。这是 T1"双模 + 契约单源"和答疑 §三"单向依赖"在替代假设下的兑现：**可替换性不是这套设计额外补的课，是它本来长这样**。

## 四、替代成本与触发条件

- **替换成本分层**：M1 对话模式 → 零成本（换宿主跑同一份命令文本）；契约与流程 → 零改动；M2 跑批 → 唯一实质成本，重写 adapter 实现。粗估 2~3 天/平台（未实测分解：adapter 实现约 1 天、代理定义迁移约 0.5 天、跑通一篇全流程验证约 1 天）；ZCode 若走 Agent 工具编排路径工作量同级。
- **什么情况才真的换**（触发条件，满足其一再启动）：
  1. pi 上游停滞或 local-custom 无法继续跟 rebase；
  2. pi 的模型接入线全部失效且无替代 provider 配置路径；
  3. 许可证或供应政策变化使 pi 不可用；
  4. 某平台出现"无人值守跑批宿主 + 只读强制 + 模型自由"三全且维护成本显著更低（截至本文各家均有缺口：ZCode 工作流受逐 run 审批与命令集冻结限制、CC 订阅绑定、OpenCode 权限配置粒度未核实）。
- **不换的默认理由**：pi 四层能力齐备且已验证到源码级，替代收益为负；替代分析的价值在于确认了**退路存在且便宜**，而不是要换。

## 五、给主方案的行动项（仅一条）

不修改主方案 v1.2 正文。若采纳本文，唯一增量是：M2 spike 验收标准加一行——**adapter 接口签名定义作为 spike 交付物之一**：`spawnAgent(definition, prompt, allowedTools, model?) → { text } | { error }`（含超时与失败契约，model 参数是分级降级在接口上的挂点）+ `runChecks()`，使"pi 实现"与"接口"从第一天就分离。其余不动。
