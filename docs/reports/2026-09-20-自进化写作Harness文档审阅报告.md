## 3. 发现清单

### 3.1 【major】`minor` 折算阈值使「首轮双净」不可达，与 §8 收敛目标直接冲突

**问题**：主方案 §4.3 规则 6 定 `minor` 按「模式标签 + 所在段落」去重累计 ≥5 折算 1 个 major → 进入修复。实现Spec §4.3 的 `EVALUATE` 把这个折算放在**每一次**评估（含 R1+R2 后的首次）。而 review-spec 的 R1 桶 13 条里 **11 条默认严重度是 minor**——一篇正常成稿几乎必然跨越阈值。

**证据**（首篇真实文章 `materials/topics/2026-09-20-AI治理十天/复审-R1.md`，11 条发现全部 minor）按 `norm(位置)` 拆键：

| 发现 | 模式标签 | 位置 | 去重键数 |
| --- | --- | --- | --- |
| R1-01 | 段落长度 | 行17、行31 | 2 |
| R1-02 | 金句数量 | 行39/43/57/59/99/101 | 6 |
| R1-03 | AI味#2 | 行35、行77、行99 | 3 |
| R1-04 | AI味#5 | 行59、行75、行99、行101 | 4 |
| R1-05 | AI味#7 | 行25 | 1 |
| R1-06 | AI味#8 | 行95 | 1 |
| R1-07 | AI味#9 | 行9、行19、行99 | 3 |
| R1-08 | 小标题风格 | 行33、行47 | 2 |
| R1-09 | 统计特征 | 行85/87/89 | 3 |
| R1-10 | 其他 | 行31、行49 | 2 |
| R1-11 | 其他 | 行23、行91 | 2 |
| **合计** | | | **29** |

阈值 `minorToMajorThreshold = 5`（`.harness/harness.config.json`）。**29 键 = 阈值的 5.8 倍**。即：**即使 R2 零发现，这篇也必然被折算出一个 major → 必然进入修复 → 必然产生 R3**。

**推论（这是本条的要害）**：
- 主方案 §4.3 流程图写的「无 → 成稿 ✅（**首轮即全净**）」在现实中近乎不可达；§8 的「**目标多数文章 2 轮收敛**」被自己的折算规则算术性否决——只要折算触发，`metrics.md` 的 R 轮数就是 3 而不是 2。
- §8 的回看规则「R≥4 占比持续 >20% 说明规格有系统性问题」随之失真：基线被抬到 3 之后，这个 20% 的判读需要重新标定。

**说明**：本篇 R2 已有 2 个 blocker，折算是否独立触发不影响本篇结果——但 29 个键数证明阈值**必然**被跨越，与结果无关。

**建议**（择一，需拍板）：
- (a) 把阈值从 5 提到与真实分布匹配的量级（首篇 29 键 → 建议 ≥20，或改为「同标签同段落**跨轮复发**才计数」）；
- (b) 折算只统计**同一标签**的去重键数（即某标签自身在 ≥5 处复发才折 1 major），而非全篇所有 minor 混算——这更贴近「同一类错反复犯」的原意；
- (c) 保留现规则但**修正 §8 的目标口径**，明确「3 轮为正常基线，2 轮是异常干净的特例」。

我倾向 (b)：它保住了「同类错反复犯才升级」的设计意图，又不让一篇有 11 处不同小瑕疵的正常稿被判为 major。无论选哪条，**§4.3 规则 6 与 §8 必须同时改**，不能只改一处。

### 3.2 【major】「其他」兜底标签参与折算，严重度语义失真

**问题**：实现Spec §1.3 规定「发现清单里出现词表外标签时解析器归一化为 `其他`」。而 `其他` 与其余标签同权参与 §4.3 的折算计数。首篇 R1-10（数字体例不统一）、R1-11（断句歧义）两条**语义无关**的零散小瑕疵都被打成 `其他`，各占 2 键。

**后果**：一个「什么都不是」的垃圾桶，会因为装了 5 件互不相关的小事而聚合出一个 major，触发一轮修复与复审。这与折算规则的设计意图（识别「同一类错反复犯」）正好相反。

**证据**：`复审-R1.md` R1-10/R1-11 模式标签均为 `其他`；`.harness/spec/pattern-tags.md` 词表含 `其他` 兜底项。

**建议**：`其他` 条目**只挂账、不参与折算**；或强制审稿人在打 `其他` 时二选一（补新标签提案 / 降为不入池的备注）。前者改一行规则，后者改审稿人 prompt。

### 3.4 【major】Node 门槛写错 + M2 缺运行环境前置（pi 本机不可运行）

**问题一：版本门槛写错。** `实现Spec §4.1` 写「**Node ≥20**、TypeScript strip-only（`node --experimental-strip-types` 或 `tsx`，零 npm 运行时依赖）」。两条都不成立：

- `--experimental-strip-types` 是 **Node ≥22.6** 才有的能力，Node 20 根本没有（本机 v22.17.1 实测 `node --experimental-strip-types -e ...` 输出 `strip-types OK`）。
- 更硬的一条：M2 的 adapter 要 spawn `pi`，而 `packages/coding-agent/package.json` 声明 `engines: { node: ">=22.19.0" }`。**实际门槛是 22.19.0，不是 20**。

**证据**：
```
$ python -c "...json.load(open('packages/coding-agent/package.json'))..."
bin: {'pi': 'dist/bundle/cli.js'}
engines: {'node': '>=22.19.0'}
$ node --version
v22.17.1          ← 本机低于 pi 声明的 22.19.0
```

**问题二：M2 缺一条硬前置——本机根本没有可运行的 `pi`。** `实现Spec §4.6` 把 M2 spike 估为「半天」，§4.7 要求「adapter 两原语在玩具稿上跑通 spawn → 文本返回」。但：

```
$ which pi                  → (not found)
$ ls "$(npm prefix -g)"     → arkcli/claude/ccr/corepack/npm... 无 pi
$ test -d node_modules      → NO
$ test -x node_modules/.bin/tsx → NO
$ ls packages/coding-agent/dist → (no dist)
$ bun --version             → command not found
```

`pi-test.sh` 的跑法是从源码经 `$SCRIPT_DIR/node_modules/.bin/tsx ... src/experimental/cli.ts` 启动——**而 `node_modules` 不存在**。仓库是一份裸克隆，既没有依赖、也没有构建产物、全局也没装 pi。

**后果**：M2 的「半天 spike」隐含了一个未写出的前置（`npm install` + 构建或全局安装 pi），且该前置的工作量与不确定性未计入任何里程碑。§10 路线图写「M2 pi 宿主 spike（半天）」，会让按文档执行的陌生工程师在第一天就卡住。

**建议**：
1. §4.1 改为「Node ≥22.19.0（对齐 pi 的 `engines`）；`--experimental-strip-types` 需 ≥22.6，或改用 tsx」；
2. §4.6/§10 增列 M2 前置步骤：「安装/构建 pi 至可 spawn 状态」并给出验收命令（`pi --version` 返回码 0），同时把本机 node 22.17.1 → ≥22.19.0 的升级列为待办；
3. 明确 M2 是 spawn **全局 `pi`** 还是 **仓库内构建产物**——这决定 adapter 的 `getPiInvocation` 怎么写（官方示例的实现在 `index.ts` 里，可直接参照）。

### 3.5 【major】终态后的「修订轮」无定义，但首篇已在跑；且与 metrics「每篇一行 append-only」冲突

**问题**：四份文档把 R 循环的终态定义为「修复后 +1 复审干净即成稿」，**没有定义成稿之后用户要求再改时的重入路径**。而这件事已经发生：首篇文章的 `任务计划.md` 有一个**未提交**的「修订轮」章节，用户指令「再审阅一遍文章，然后结合国内外拿用户数据的案例加入进来讨论」，计划里自行发明了 S8 案例调研 → S9 案例入文 → **R4 复审** → S10 修复到终态（R5 按需）。

**证据**（`git diff -- materials/topics/2026-09-20-AI治理十天/任务计划.md`，+16 行）：
```
## 修订轮（2026-09-20 用户指令：...）
| S8 数据案例调研 | ... | pending |
| S9 案例讨论入文 | ... | pending |
| R4 复审 | 子代理（新进程） | ... | R4 | pending |
| S10 修复到终态 | fixer + reviewer | ... | R5（按需） | pending |
```
计划本身**做得很对**（复用了 R 循环、走新进程、机核每轮全绿、R5 按需），问题是它是**规格外行为**：没有 ReviewSpec 条目定义「修订轮」的审阅范围，没有规则说明修订轮是否重新计算 minor 折算（§4.3 规则 6 是「全篇累计」，修订轮加进来后旧 minor 是否重新计数？），也没有说明修订轮的轮次是否计入软上限 R5 的同一预算。

**连带冲突**：`实现Spec §1.6` 定 `metrics.md`「每篇一行」且 **append-only**。同一篇文章现在走了 R1/R2/R3 又走 R4/R5——**更新原行违反 append-only，追加第二行违反「每篇一行」**。两条规则在此场景下无法同时满足。

**建议**：补一节「§4.5 修订轮（终态后重入）」：定义触发（用户指令）、范围（全篇重审还是仅改动段）、折算计数是否清零、轮次预算是否共用 R5、metrics 记法（建议：`备注` 列记「含修订轮 R4-R5」，R 轮数记累计值，仍保持每篇一行 append-only 语义）。

`实现Spec §5` 声明了 M2 的三处有意收窄（仅 R 循环、S3 腿归 M2.5+、`createAgentSession` 宿主被 spawn CLI 取代），但 `主方案 §3.1` 仍写「跑批模式（新增）：`harness/run.ts` 用 `createAgentSession({ tools, customTools })` 起宿主」、§10 仍写 M2 验收「跑通 S3→R1→R2 全程」。§6 给了「冲突以主方案为纲，唯 §5 已声明的偏离除外」的豁免，但**主方案正文未标注该豁免**，两份定稿文档在这一点上仍互相矛盾。建议在主方案 §3.1/§10 各加一行指向实现Spec §5。

### 3.8 【minor】精读类 `修辞-R1` 的适用边界只圈了「AI味/声音类」

主方案 §3.2 模板 B 映射表写「R1 的 **AI 味/声音类**检查只施于自述部分；直译与原文框以忠实为先、不做修辞审阅」。但 review-spec 的 `修辞-R1` 桶里还有**非修辞项**：`错别字`(major)、`代码规范`、`注释格式`、`二维码`。这些对精读稿的直译部分是否适用，**没有定义**——「错别字」按字面应查全篇（含译文），但按「R1 只施于自述部分」则不查译文。建议在 ReviewSpec 里给这几条加显式的适用域标注。

### 3.9 【minor】代码行宽双归属

`修辞-R1` 的「代码片段输入规范」条目自带括注「（行宽部分机核可查）」但**未标机核化**；`事实-R2` 的「机核体检」条目已标 `·[机核化:check_basics.py]` 且 `check_basics.py` 确实查行宽（L2 docstring 第 3 项）。同一检查落在两个视角桶里，且一个标机核化一个没标，会让「审稿人只复核不重查」的边界模糊。建议 R1 条删去行宽子项，统一归 R2 机核体检。

### 3.10 【minor】`复审-R{n}.md` 的落盘目录未在任何 spec 中钉死

实现Spec §2.1 给了 `复审-R{n}.md` 的**内容模板**，§4.3 说 COLLECT「落盘 复审-R1.md、复审-R2.md」，但**没有一份文档规定它落在哪个目录**。实际落在 `materials/topics/<选题>/`（主方案 §5.1 的措辞「output/ 下的 任务计划.md、复审记录.md…照旧落调研包」本身歧义——实际这些文件**不在** `output/` 下，而在调研包）。M2 的 `run.ts`/`parse.ts` 必须有确定性路径才能读回，建议在 §2.1 明确「复审产物落 `<调研包>/复审-R{n}.md`，路径由任务计划给出」。

### 3.11 【minor】四份文档自身的审阅产物不符合本 spec §2.1 契约

设计 §9 声明本文档「吃自己的狗粮」按 §4 循环审阅。但四份复审记录的实际格式是 **5 列**（`ID | 严重度 | 位置 | 问题 | 建议`），而 §2.1 要求 **7 列**（含 `类别`、`模式标签`、`建议动作`），且**全部没有 `模式标签` 列、没有「正面发现」栏**。

**后果不是格式洁癖**：没有 `模式标签`，这些发现就**无法按标签聚类进 `lessons/pending.md`**——即这套 Harness 的头几轮真实审阅，产出的数据是它自己的进化层**读不了**的。同理，「正面发现」栏全缺 → 出口④（样本库扩充）至今零输入。

**建议**：把已落地的四份复审记录视为「文档审阅」而非「文章审阅」，在 §9 注明文档类审阅豁免 §2.1 契约；或后续补齐标签列。**更重要的推论**：这说明 §2.1 契约只在文章链路上被执行，文档链路是例外——若希望进化层未来也吃文档审阅数据，需要显式设计。

### 3.12 【minor】影子验证的小样本与退役周期未定义

`§5.3` 步骤 3：误报率 >50% 打回。回看篇数默认 3（`shadowLookbackArticles`），若 3 篇只命中 2 次，则「1 误报 / 2 命中 = 50%」正好卡在边界，统计噪声极大。步骤 5「连续 2 个**周期**零命中或纯误报 → 退役」——「周期」未定义时长（月度？毕业周期？）。建议补最小命中样本数（如命中 <5 条时不判误报率，转人工判断）与「周期 = 一次月度回看」。

### 3.13 【minor】分支仅存本地；文档在 pi fork 仓、实现在 article-system 仓

`git ls-remote --heads origin | grep self-evolving` 无命中 → `feat/self-evolving-writing-harness` **未推送**（origin 为 `git@github.com:alittleseven/pi.git`，用户自有 fork）。同时 `docs/` 目录在 `main` 上不存在，即这批文档**只存在于这一个分支、这一台机器**；而实现落在另一个仓（article-system）。跨仓 + 单点存储的组合，一旦本地仓损坏，设计意图与实现依据会同时失去索引。建议：推送该分支到自有 fork（**远程操作，需 Human 确认**），或在 article-system 侧留一份指向本报告的指针。

## 4. 文档质量亮点（供后续文档参照）

1. **替代分析的事实分级**（【验·实测】/【验·记忆】/【引】/【无】）——把「我实测过」和「我引述的」显式分开，并在 R2 修订时**把夸大的【验】降级为【引】**（J1/J2）。这是本工作区 W3 的教科书级执行。

4. **§4.2 的「正面发现」栏**：在设计审阅流程时就预留了「只收敛不犯错」之外的第二条积累路径——这是很少见的自觉。
